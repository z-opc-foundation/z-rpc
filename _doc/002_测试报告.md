- 被测：`io.github.yuku123:z-rpc:1.0.2`，16 个模块 / 114 个 Java 主源文件
- 环境：JDK 25.0.2 (Corretto) + Maven 3.9.14，macOS aarch64
- 时间：2026-09-25 首测，2026-09-26 修复轮 / api 轮 / core 轮 / 扩展层轮 / 上下文轮 / 跨进程轮（数字全部由 `mvn` 实跑与 `~/.cache/zrpc_gauges/zrpc_tally.sh` 读取 `target/surefire-reports/*.xml` 得到，非估算；量具与日志不放 `/tmp` —— 这台机器上 `/tmp` 会被别的会话扫走）

## 0. 一句话结论

z-rpc 此前**一个测试都没有**（测试文件基线 = 0）。本次补齐 **45 个测试源文件 / 472 条实跑用例 = 反应堆内 460 + admin 12，0 failure、0 error、0 skipped**；
过程里坐实的缺陷全部编号列在 §2（首测的 C/H/M/R + 修复轮新发现的 N1–N2 + api 轮新发现的 N3–N11 + core 轮新发现的 C4、H13、H14、N12–N18 + 扩展层轮/上下文轮/跨进程轮新发现的 N19–N26）；**当前以 `bug_` 前缀钉住"实际行为"的用例 = 121 条**（HEAD 基线 69 → 扩展层轮 +43（filter 10 / metrics 16 / async 13 / mock 4）→ 上下文轮 +9 = 121；跨进程轮 +0，它新增的两条用例一个是正向断言、一个是 §7 第 25 行的修复验证），复算命令：
`grep -rhoE "void (bug_[A-Za-z0-9_]+)\(" --include='*.java' */src/test | sort | uniq | wc -l` = 121，把 `uniq` 换成 `uniq -d` 输出为空（去重前后同数，即**没有重名**；这一条不是废话：扩展层轮就抓到过一次跨模块重名，见 §5）。
四轮合计在 `src/main` 落了 **25 处改动**（§7 逐条列）：§2 点名的缺陷里 **C1（只消费侧）、C2、C3、C4、H1、H2、H5、H6、H7、H10、H11、H12、H13、H14，外加 H8 的 `async`/`oneway`/`registry` 三项、H9 的 CGLIB 丢注解与多接口只导第一个两项、M4、M5**，
以及两条未编号接线空洞（`ZRpcReferenceInjector` 从没被注册过、`@ZRpcService` 不是 stereotype）和 N2（`RegistryService` 零实现，已补实现）；N1（双份序列化注册表）也已合流。api 层的 N3（代理把接口声明的 `equals(String)` 当成 `Object.equals` 吞掉）也已修。第 25 处是跨进程轮量出来的 **N27 = H7 的读侧残留**（一条裸键注册替该接口**所有**版本冒充应答），它只在两个 JVM 的形态下才看得见。
C1 只修了**消费侧**：默认协议现在真发 Netty 往返，同 JVM 双端 socket 实测拿到 `echo:world`；provider 侧 `export()` 仍不绑端口，钉在 `exportStillBindsNothing`。
core 轮修掉三条**资源级**缺陷：`ServiceConfig.unexport()` 在 server 走阻塞模式时**永久死锁**（C4，实测把整条 mvn 挂住 10 分钟、且**一条测试都没变红**），以及 `RpcServer` 绑定失败 / `RpcClient` 连接失败各自漏掉一组非守护 EventLoop 线程（H13、H14，判据是 `nioEventLoopGroup-<poolId>-<n>` 里 poolId 的水位线）。
上下文轮 + 跨进程轮把"链路到底传了什么"第一次钉死：**附件确实跨过真实 socket、也确实跨过 JVM 边界**（含调用方自己的键），而 **provider 侧的 MDC 还原与 provider 侧指标在真实链路上一个都不生效**（N19），**`group` 在服务端路由里完全不存在**（N20），**`RpcClientHolder` 缓存的客户端一旦关掉就永久毒化且 timeout 传染**（N21）。

### Critical

**C1 [实测] 默认协议的 `invoke()` 不发任何网络请求** — `z-rpc-protocol/.../ZRpcProtocolImpl.java:98-103`
`ZRpcInvoker.invoke()` 直接 `return new Result.RpcResult("Z-RPC invocation result for " + methodName + " on " + type)`，注释写着"简化实现"。
而 `"z-rpc"` 既是 `ProtocolConstants.DEFAULT_PROTOCOL`，又是 `@SPI("z-rpc")` 的默认扩展名，还登记在 `META-INF/z-rpc/com.zifang.z.rpc.api.Protocol` 里。
后果：用默认协议消费一个 `UserService`，拿到的是一个**看起来像成功的字符串**，返回值类型 `T` 是业务接口 —— 强转即 `ClassCastException`，或被上层当成正常响应静默吞掉。
**修复轮状态：消费侧已改** —— `ZRpcInvoker.invoke()` 现在经 `RpcClient` 做真实 Netty 往返，异常折成 `Result.error(RpcException.network(...))`；`ConsumerRoundTripE2ETest` 在真 socket 上取回 `echo:world`（7 条，见 §4）。**provider 侧 `export()` 仍是不绑端口的空壳**，钉在 `exportStillBindsNothing`。

**C2 [实测] 4 个 SPI 接口没有 `@SPI` 注解，它们的登记表全是死文件** — `ExtensionLoader.java:94`
全仓 `@SPI` 只出现在 3 处（`Filter` / `Protocol` / `ProxyFactory`）。但 `META-INF/z-rpc/` 下却有 4 份指向未注解接口的清单：

| 登记表文件 | 登记的 key | `getExtensionLoader()` 结果 |
|---|---|---|
| `...cluster.Cluster` | failover/failfast/failsafe/failback/broadcast | `IllegalArgumentException: ... is not annotated with @SPI` |
| `...loadbalance.LoadBalance` | random/roundrobin/leastactive | 同上 |
| `...serialize.Serialization` | java/json/hessian2/kryo/protobuf | 同上 |
| `...registry.RegistryService` | z-config/in-memory/zknaming | 同上 |

对照成立：打了注解的 `Protocol` / `ProxyFactory` 走同一条路就能拿到 `names=[z-rpc]` / `names=[jdk]`。
`SpiRegistrationLivenessTest`（6 条，全绿）把这件事钉住了：先证明资源文件在 `ClassLoader.getSystemResource` 里取得到、5 个 Cluster 类和 3 个 LoadBalance 类全都 `isAssignableFrom` 通过 —— **只差一个注解**。

**C3 [实测] starter 在 `source=8` 下调 JDK 9 才有的 `Field#canAccess(Object)`** — `ZRpcReferenceInjector.java:52`
本模块 `maven.compiler.source/target = 8` 且**没用 `--release`**。同文件同 classpath 的对照实跑：
`javac -source 8 -target 8` → 通过（它拿 JDK 25 的类库解析）；`javac --release 8` → `cannot find symbol: method canAccess(Object)`。
后果：产物在真 JDK 8 上运行到 `@ZRpcReference` 注入时 `NoSuchMethodError`。
用例 `bug_referenceInjector_bytecode_needs_Java9_canAccess` 用**字节码常量池字节扫描**找 `"canAccess"`，不依赖编译器版本，所以不会因为本机 JDK 升级而漏判。

**C4 [实测] `RpcServer.start()` 在监视器内阻塞 ⇒ 任何声明式导出的服务都关不掉** — `RpcServer.java:93-95/150` + `ServiceConfig.java:258-265`
`start(boolean daemon)` 原来整块 `synchronized (this)`，而阻塞分支（`start()` → `start(false)`）在锁内做 `channel.closeFuture().await()`；`stop()` 又是 `synchronized`。`ServiceConfig.startRpcServer()` 恰好用一条常驻线程 `ZRpcServer-<port>` 走阻塞分支 ⇒ 该线程**永久持有 `RpcServer` 的监视器**，`unexport()` → `doUnexport()` → `rpcServer.stop()` 在锁上无限等待。更糟的是 `doUnexport` 把 `stop()` 包在 `catch (Exception)` 里，而阻塞不是异常，所以没有任何一处会报错。
这一条**不会变红**，只会让 `mvn test` 静默卡住：本轮首跑在这里挂了 10 分钟（0 条 failure / error，栈顶停在 `ServiceConfigTest.serviceUrlCarriesConfig:172`），靠 `jps` + `jstack` 而不是靠红色定位。
**core 轮已修**（§7 第 22 行）：`synchronized` 块收缩到"建两组 group + bind + 置 `started`"，`await` 移到监视器之外。守它的用例 `unexportReturnsWhileTheServerThreadIsParkedInsideStart`：先轮询线程栈直到它真的停在 `RpcServer.start` 帧内，再把 `unexport()` 丢进 `ExecutorService` 并 `get(10, SECONDS)` —— 修复前必超时（超时消息里写明了"十分钟也不会返回"的原因）。

### High

**H1 [实测] 定长头实测 26 字节，`ProtocolConstants.HEADER_LENGTH` 写 24** — `ProtocolConstants.java:23` vs `ZRpcMessageEncoder`
编码器写 `4 magic + 1 version + 1 msgType + 1 serId + 1 compress + 2 status + 8 reqId + 4 bodyLen + 2 headerLen + 2 reserved = 26`。
解码器用 `readableBytes() < HEADER_LENGTH` 当"够不够一帧"的门限，随后还要 `readShort()` 两次。
`FrameCodecTest` 实测：喂 23 字节 → 安静等待（对）；喂 **24 / 25 字节 → `IndexOutOfBoundsException`**（`readerIndex(24) + length(2) exceeds writerIndex(24)`）；喂 26 字节 → 正常。
即半包正好停在 24/25 字节这条边界上必抛，`ByteToMessageDecoder` 会把异常冒泡出 pipeline 并关连接。门限比真实头短 2 字节 ⇒ 门限形同虚设。

**H2 [实测] `Serialization` 的 id 空间：未知 id 静默回落到 Hessian2** — `SerializationFactory.get(byte)`
`get((byte)0)`、`get((byte)6)`、`get((byte)99)` 全部返回 `Hessian2Serialization`，只打一行 WARN。
对端把序列化器配错时不会立刻失败，而是用错的解码器去解 —— 变成乱码或下游莫名异常。对照：`getByName("protostuff")` / `""` / `null` 一律返回 **null 而不抛错**，调用方第一个动作就是 NPE（用例把这条 NPE 也跑出来了）。
**修复轮状态：已修** —— 未知 id 抛 `RpcException.serialization`（消息里带上那个 id 和已注册清单），未知 name 抛 `RpcException.config`（带上支持列表），`null` 抛 `IllegalArgumentException`。用例翻成 `unknownIdFailsFastInsteadOfFallingBack` / `unknownNameFailsFastInsteadOfReturningNull`。

**H3 [实测] JSON 序列化把 Map 打成空 Map：条目静默丢失** — `JsonSerialization`
`serialize({list:[1,2,3], nested:Pojo})` 出来有字节，`deserialize(bytes, LinkedHashMap.class)` 回来是一个 **size=0 的 Map**。
同一份数据 java / hessian2 / kryo 都拿回 2 个条目；POJO 目标类型反倒是好的 —— 丢数据只发生在"目标类型是容器"这条路径上。

**H4 [实测] `protobuf` 宣称支持、实际只吃 `MessageLite`** — `ProtobufSerialization`
`serialize(POJO)` / `serialize("hello")` / `serialize(42)` 全抛 `RpcException: ProtobufSerialization only supports com.google.protobuf.MessageLite`。
仓库里没有任何 `.proto` 生成类，所以 `SERIALIZE_PROTOBUF=5` 这个 id、`META-INF/z-rpc/...Serialization` 里的 `protobuf=` 一行、以及 `z.rpc.*.serialization=protobuf` 配置项都不可用。
附带一条不对称：`serialize(null)` 却**绕过**类型检查返回空数组，五个实现都是 `len=0`。

**H5 [实测] `getActivateExtension()` 从不触发加载，冷加载器上永远返回空** — `ExtensionLoader`
`cachedActivates` 只在 `loadExtensionClasses()` 里填充，而 `getActivateExtension(groups)` 直接读这张表。
`ColdDemoSPI` 夹具实测：冷 loader 上 `getActivateExtension("consumer")` = **空**；先调一次 `getExtensionNames()` 再调它 = 2 条且按 `@Activate.order` 升序（coldB=10 → coldA=20）。

**H13 [实测] `RpcServer` 绑定失败留下两组永不退出的非守护 EventLoop 线程** — `RpcServer.java:96-97/120`
`bossGroup`/`workerGroup` 在 `bind()` 之前就已构造，`bind(host, port)` 一抛（端口被占、地址不可用）就顺着 `start()` 抛出，两个 group 从来没人 `shutdownGracefully()`。Netty 的 EventLoop 线程是**非守护**的 ⇒ 一次失败的启动就足以让 JVM 永不退出；反复重试则每次泄漏 `1 + CPU 核数` 条线程。

量具：`failedBindShutsTheEventLoopGroupsDown` 用 `nioEventLoopGroup-<poolId>-<serial>` 里的 **poolId 水位线**判定 —— poolId 是 Netty 的全局单调计数器，每建一个 group 加 1，所以"泄漏"表现为水位线被推高却数不到对应活线程。

**H14 [实测] `RpcClient` 构造期连接失败漏掉整个 EventLoopGroup** — `RpcClient.java:36-41/61-71`
构造器直接 `connect()`，`connect()` 先 `new NioEventLoopGroup()` 再 `bootstrap.connect(...).sync()`；连不上时抛 `RuntimeException`，而这个 client 对象永远不会被使用 ⇒ **没人会调 `close()`**，那组非守护线程就留下了。这是"构造函数里做网络 I/O"（R3 的另一半）的连带后果。
**core 轮已修**（§7 第 24 行）：两个 catch 分支都先 `releaseGroupAfterFailedConnect()` 再抛。
量具：`failedConnectReleasesItsEventLoopGroup`（同一把水位线尺），配对照用例 `closedClientReleasesItsEventLoopGroup`。对照那条**第一版是假红**：它原来拿真 `RpcServer` 当监听端，而 server 的 worker group 在取 `before` 读数时还没有活线程、之后才出现，poolId 比 client 那组大 ⇒ 被我的尺读成"client 泄漏"。改法是让对照只借一个裸 `ServerSocket`（能完成 TCP 握手就够），把被测对象自己的 group 隔离出来。

### api 层（api 轮给 `z-rpc-api` 补首批测试时坐实，N3–N11）

`z-rpc-api` 此前零测试，而它是**所有人都会经过的那一层**：`Invoker` / `Invocation` / `Result` / `ProxyFactory` / `Protocol` / `Filter` 六个契约接口加两个实现类。补齐 53 条用例后量到 8 条：

**N3 [实测] `JdkProxyFactory` 的代理把接口自己声明的 `equals(String)` 当成 `Object.equals` 吞掉** — 拦截条件原来只有"方法名 + 参数个数"，`boolean equals(String other)` 这种合法重载拿到的永远是 `proxy == args[0]` 即 `false`，**一次网络请求都不发、也不报错**。

**N13 [实测] 注册中心的唯一赋值点被注释掉了，两侧的后续调用于是必然 NPE、且 NPE 被吞**（3 条）

`bug_versionIsDroppedOnRegistration`：服务 URL 上带着 `version=2.3.4`，而 `RpcServer` 的路由表里只有裸接口名 —— §7 第 6/7 行修的是 `register(Class, Object, String)` 这个重载，`ServiceConfig.startRpcServer()` 走的是 `registerService(Class, Object)`，压根没经过被修的那条路。`bug_versionIsDroppedOnTheWayOut`：引用侧要 `5.0.0`，拿回来的仍是默认实现。`bug_providersAreKeyedByAddressOnly`：`RegistryDirectory` 的 `urlInvokerMap` 以 `getAddress()`（host:port）为键，**同地址注册两个版本只剩一条**，留下谁取决于推送顺序 —— 也就是说即便两侧都不丢版本，目录这一层也没有版本维度。**H7 的修复因此只覆盖了手工注册，声明式导出仍在互相覆盖。**

**N15 [实测] 四项配置写进去没人读**（4 条）
`bug_timeoutSettingIsWriteOnly`（`timeout=50` 挡不住 3s 的默认超时，落到 `RpcClient` 的字段常量）、`bug_clusterSettingIsIgnored`（换策略名拿到的还是 failover —— 与 N12 同因：那个名字即使能解析，core 的 `Cluster` 也没 `@SPI`）、`bug_loadBalanceSettingIsNeverConsulted`（策略名随便写也不报错）、`bug_protocolSettingDoesNotChangeTheFrame`（写 `thrift`，线上跑的仍是 `z-rpc-remoting` 的 10 字节帧 + Java 原生序列化）。这是 H8/H9"属性有 setter 无落点"在 core 侧的续集。

**N16 [实测] `FailoverCluster` 的重试语义有五处与名字相反**（5 条）
`bug_firstAttemptSkipsFirstInvoker`：`select(invokers, lastIndex=0, …)` 在 `size ≥ 2` 时返回 `get(1)` ⇒ **首次尝试永远跳过 provider #0**，第一位只在重试时才轮到（这条本轮把我自己的用例红了一次，见 §5）；`bug_errorResultIsNotRetried`：只有**抛出**的失败才重试，用 `Result` 携带异常的 invoker 一次都不重试；`bug_isAvailableIgnoresInvokerHealth`：`isAvailable()` 只看目录空不空，全挂的 invoker 也算"可用"；`bug_negativeRetriesReachesUnreachableThrow`：`retries=-1` 时循环体一次不进，落到代码末尾那句 `IllegalStateException("Should never reach here")` —— 报错信息指向一行不可达代码；`bug_noProviderThrowsPlainIllegalState`：无 provider 抛裸 `IllegalStateException` 而非 `RpcException.noProvider`（`FailfastCluster` 用的才是后者），而 `RpcException extends RuntimeException` 与它平级，**上层按 `RpcException` catch 必然漏**。

**N17 [实测] 目录层的十个洞**（`AbstractDirectory` 5 + `RegistryDirectory` 5）
`bug_routerPriorityIsNeverApplied`（`route()` 按 `routers` 加入顺序执行，`getPriority()` 从不参与排序；且任一 router 返回空表就整体返回空表）、`bug_setInvokersLetsNullElementsThrough`（`addInvoker` 挡 null，`setInvokers` 不挡，null 元素能一路进到 `list()`）、`bug_nullParameterBricksDirectoryConstruction`（URL 收得下 value 为 null 的参数，目录构造时炸）、`bug_queryMapIsOneShotSnapshot`（`queryMap` 是构造时的一次性快照，之后再往 URL 上加的参数目录永远看不见 —— 而 `ServiceConfig`/`ReferenceConfig` 正是先建 URL 再逐项 `addParameter` 的）、`bug_urlParametersEscapeByReference`（`URL.getParameters()` 交出的是**活映射**，外面一句 `put` 就能把已构造对象的地址改脏；这是 `common.URL` 的暴露面，目录只是受害者之一，与 §8 里 `setParameters(null)` 那条同形状）、`bug_emptyNotificationIsIgnored`（注册中心推空表时旧 provider 全部留着 ⇒ **服务下线在客户端永不生效**）、`bug_subscribeFailureIsSwallowed`（注册中心抛异常只打日志，目录"健康"地空着）、`bug_nullRegistryIsAccepted`（null registry 能构造，直到调用才报"没有 provider"）、`bug_inheritedMutatorsAreIgnoredByDoList`（`RegistryDirectory` 覆写 `doList` 之后，继承来的 `addInvoker`/`setInvokers` 变成静默无效 —— 调了，改了，`list()` 不受影响）、`bug_oneFailureBricksTheInvoker`（一次失败把该 invoker 永久打掉且不重建；猎物是同一条链上**新建**的目录仍能打通，证明缺的是重连而不是地址）。
另有一条不算缺陷但会误导人的形状：两参构造把**同一个** `URL` 对象同时当目录 URL 与消费者 URL（`twoArgCtorAliasesUrls`），改一个等于改两个。

**N18 [实测] 导出生命周期与地址发布的六个假信号**（`ServiceConfig` 4 + `ReferenceConfig` 2）

### 扩展层（扩展层轮给 filter / metrics / async / mock 补首批测试时坐实，N19–N22）

四个模块此前都是**零测试**（filter 4 文件 / 134 行、metrics 3 / 292、async 2 / 174、mock 1 / 37）。补到 24 / 31 / 27 / 8 条，其中 43 条 `bug_`。一条都没修 —— 判据与 §8 相同：这一层的缺陷全是"没人调用的代码写错了"，修它们要先把"谁该调用"定下来（N19 就是这件事本身）。

**N19 [实测] 过滤器体系是完整可加载的，但 `src/main` 里没有任何一处装配它**（10 条，`z-rpc-filter`）
`grep -rn "getActivateExtension" --include='*.java' . | grep -v '/src/test/'` 只有 3 个命中，全在 `z-rpc-spi` 自己文件里（javadoc 一处、方法声明一处、`@Activate` 的注释一处）⇒ **生产代码零调用方**。而 SPI 侧一切正常：`allFourNamesAreLoadable`、consumer 侧顺序 `ConsumerTraceFilter(10) → MonitorFilter(100)`、provider 侧 `ProviderContextFilter(10) → ProviderMonitorFilter(100)`、`@Activate` 的 group/order 运行时读得到、实例按名字缓存成单例。缺口有两层：库里**没有链对象**（`bug_thereIsNoChainObject` —— 所谓"责任链"只有一个返回 `List` 的加载器，没有任何东西按 order 把 `Invoker` 包起来），以及真实服务端 `RpcServerHandler` 是拿 `RpcRequest` 直接反射调 POJO（N23 是这个缺口的后果）。剩下 9 条（`BuiltInFilterBehaviorTest`）钉的是"**就算接上也会错**"：invoker 抛异常时 `MonitorFilter` 把原始异常降级成 `RuntimeException` 的 cause（`bug_monitorFilterWrapsTheOriginalThrowable`）而 provider 侧原样重抛（`bug_providerMonitorRethrowsTheOriginal`，两侧不对称）、null 结果在消费侧变包装过的 NPE、在服务侧变裸 NPE、两侧监控过滤器**共用同一个 key** 因而 provider 耗时与 consumer 耗时并进同一个桶、`ProviderContextFilter` 的 `clearAll` 顺手抹掉别人的 MDC 键、上游传进来的 `trace-id` 被本地线程计数器无条件覆盖、以及"traceId 绑线程不绑调用"。

**N20 [实测] 直方图的分位数在"空表"和"负样本"两种输入下报的是桶边界，不是数据**（16 条，`z-rpc-metrics`）
`bug_quantileOfEmptyHistogramIsNotZero`：新建的空桶 `getQuantile(0.5)` 报 **58**（第一个桶的上界）而 `total=0` —— 这一条同时被 `MetricsCollector` 的 `bug_aFreshBucketAlreadyReportsNonZeroPercentiles` 从收集器侧面钉住。`bug_anyQuantileBelowOneIsTheFirstBucket`：q<1 一律返回 58，与样本无关；`bug_negativeSamplesAreDroppedSilently`：负数样本既不计数也不报错；`bug_zeroBucketHistogramThrowsOnRead`：`bucketCount=0` 的直方图读分位数直接越界抛异常。javadoc 写指数分布，实测桶边界是**等差**（`bug_` 之外的那条正向用例量出默认边界 58 / 117 / 30000 / 60000）。并发侧两条：`counts` 是普通 `long[]` 而 `total` 是 `AtomicLong` ⇒ 桶更新不原子，实测 `sum(counts) <= total` 有缺口；`MetricsCollector.snapshot()` 是**浅拷贝**，桶对象还在被写，快照会自己长大；`service` 名里带冒号时两个不同服务并成同一个桶（键的拼法是 `service + ':' + method` 裸拼）。`MetricsReporter` 的 6 条则是生命周期：`started` 挡板是 check-then-act（并发 `start` 能排进两个周期任务）、`stop` 是终局操作（再 `start` 抛 `RejectedExecutionException` 且 `started` 卡在 true，连"没 start 过就 stop"也会废掉实例）、非法 interval 抛异常后同样把 `started` 留在 true，而所谓"上报"只有日志 —— `bug_reportingHasNoTransport` 直接读该类的 class 字节扫常量池，**`java/net`、`Socket`、`Http`、`admin` 一个都不出现**（猎物 = 同一份字节里 `MetricsCollector` / `snapshot` / `report` 三个名字都在，证明不是"没读到内容"）。

**N21 [实测] `async` 模块的 `DefaultFuture` 不是一张 Future，而它的登记表没有清理入口**（13 条，`z-rpc-async`）
`pom`/javadoc 承诺的 `AsyncRpcResult` 这个类**根本不存在**（`bug_advertisedAsyncRpcResultIsMissing`），`DefaultFuture` 也**不实现任何接口** —— `getInterfaces()` 实测是空表 `[]`，而 `get()` / `isDone()` 这些方法名倒全对得上（`bug_defaultFutureIsNotAFuture` 的猎物就是这几个名字），所以它看起来像 Future 而类型上不是；更没有"把一个已完成响应交给 `Result`"的构造（`bug_futureCannotBeHandedToAResult`）。`DefaultFutureTest` 里 5 条：超时后到达的响应被静默丢弃（无回调无指标）、**requestId 撞号时前一个调用方永远拿不到自己的响应**（`FUTURES` 以 id 单键）、被中断时 `get()` 既不抛也不清理直接 `return null`、没人 `take` 的 future 永远躺在 `FUTURES` 里且**没有任何清理入口**、对外只有无参 `get()`（没有 `cancel`、没有 `get(long, TimeUnit)`）。另两条观察：`get()` 是 10ms 轮询，真实等待比 timeout 多出最多一个轮询片；`RpcContext` 的 `internal` 表没有任何公开入口（死存储），`spanId` 恒为 "0" 且无写入口，javadoc 承诺的 `token` 不存在。

**N22 [实测] `z-rpc-mock` 整模块只有一个不是扩展点的接口，pom 承诺的两个类不存在**（8 条，`z-rpc-mock`）
`GenericService` 没有 `@SPI`、没有元文件（`bug_genericServiceIsNotAnExtensionPoint`），`$invokeMap` 只转发 `values()` ⇒ **键名在实现方那里彻底消失**，`paramTypes` 取实参运行时类 ⇒ 子类被报成子类、null 只能报成 `Object`（泛化调用的服务端签名匹配据此必然错），`(null, null)` 与"两个零长数组"是两种不同形状。`MockClusterInvoker` / `PojoUtils` 在本模块不存在（R5 的续集：README 宣传的 mock 支持在代码里没有宿主）。

### 上下文与跨进程（上下文轮 +11 条、跨进程轮 +5 条正向用例 + 1 处修复，N23–N27）

这一轮的目标不是补覆盖率，是回答"**一次真实的远程调用到底带走了什么**"。量具从同 JVM 真 socket（`ContextPropagationE2ETest`，11 条）升级到**两个 JVM**（`CrossProcessE2ETest` 5 条 + `CrossProcessProvider` 子进程夹具）。

**N23 [实测] provider 侧的上下文还原与指标产出，在真实链路上一个都不生效**（2 条，同 JVM 真 socket 量实）
`bug_providerBusinessCodeSeesNoTraceId`：消费端 `ConsumerTraceFilter` 写的 `trace-id` **确实跨过了 socket**（对端 handler 收到的 `RpcRequest` 附件里读得到，`traceAttachmentCrossesTheRealSocket` 钉住），但业务方法里 `ThreadContext`/MDC 取到的是 `null` —— 服务端从不运行 `ProviderContextFilter`。猎物是同一条链上手工挂上该过滤器就能还原 traceId 并在返回后清干净。`bug_providerMetricsAreNeverRecordedOnTheRealPath`：真实服务端挨了一次抛异常的执行之后 `MetricsCollector.getAll()` 仍是空表；手工挂 `ProviderMonitorFilter` 立刻产出 1 个桶（`error=1`、`success=0`）。⇒ 真实服务端这一次执行**在收集器里不留任何痕迹**，所以"provider 侧指标"这一列在链路上没有生产者。顺带把话说全：`grep -rn "MetricsCollector" z-rpc-admin/src/main` 命中 **0** —— admin 面板读的是它自己的存储，与这套收集器之间本来就没有桥（收集器一侧也没有出口，见 N20 的 `MetricsReporter`）。

**N24 [实测] 消费端与服务端对"路由键"的算法不一致，group 在服务端根本不存在**（2 条）
`bug_groupScopedRegistrationIsUnreachable`：`URL.getServiceKey()` 拼的是 `gray/com.X:1.0.0`（含 group），而 `RpcServer.serviceKey(name, version)` 只看 version ⇒ 按消费端的键形状注册的服务**永远命中不了**；同一接口的 group 维度在两侧一个是键的一部分、一个完全被忽略。`bug_defaultVersionStealsTheBareKeyRegistration` + `RpcRequest.DEFAULT_VERSION`（§7 第 25 行）合起来说明缺省值这一维也有同样的错位：不带 `version` 附件的请求在服务端被物化成 "1.0.0"，于是表里若同时有 `:1.0.0` 和裸键两条注册，前者抢走请求 —— 请求方"没说要哪个版本"这个事实在跨越 `RpcRequest` 时丢失。

**N25 [实测] `RpcClientHolder` 以 `host:port` 为键发还同一个客户端：关掉的客户端永久留在缓存里，第一个调用方的 timeout 传染所有人**（2 条）
`bug_closedClientIsPoisonForever`：某处 `close()` 之后，缓存条目不摘，之后每次经 holder 的调用都失败（这条与 core 轮 N18 的 `bug_destroyTakesDownSharedRegistry` 是同一形状的第二个实例：**共享对象的生死由某个调用方决定**）。`bug_holderSharesOneClientPerAddress`：反射读回 `RpcClient.timeout` 证明两次不同参数拿到的确实是**同一个对象** —— 先设 50ms 的人决定了后来所有人的超时。holder 对外只有 `get`/`invoke` 两个方法（用 `isSynthetic()` 过滤后逐个点名），没有任何失效、驱逐或按参数分片的入口。

**N26 [实测] `RpcClient` 用 URL 的 version/group 无条件覆写调用方同名附件**（1 条正向 + 1 条 bug）
`urlAttachmentsClobberCallerOnTheWire`（正向：URL 上的值确实上了线，包括调用方自己塞的其它键一起透传）与 `bug_nullUrlVersionErasesCallerVersion`：URL 未设 version 时，调用方**显式**给的 `version` 附件被覆成 `null` —— 覆写不区分"URL 有值"和"URL 没值"，所以配置对象能反向擦掉调用方的意图。



**N27 [实测·已修] 一条裸键注册替该接口的所有版本冒充应答** —— 跨进程轮唯一一次动 `src/main`（§7 第 25 行）。同 JVM 的 `EmbeddedChannel` 用例看不见它（注册表两边共用，写法一致就测不出错位）；只有第二个 JVM 把 `8.8.8` 的请求交给裸键 provider 应答时才现形。第一版修法（"该接口只要有带版本登记就一律不退裸键"）把 `RegistryDirectoryTest.bug_versionIsDroppedOnTheWayOut` 打红了一次，见 §5。

## 5. 取证过程里被推翻的判定（避免下一个人重踩）

- 我最初断言"远端连不上时字段留 null"。实测返回的是 `FailoverClusterInvoker` 上的 JDK 代理 ⇒ 改成更强的结论 H8（`check=true` 形同虚设）。
- 并行代理产出的 `RpcExceptionTest` 用了 `java.lang.reflect.Modifier.ModifierLike`（在 `-source 8` 下 `cannot find symbol`）和一条恒等断言 `length - 3 + 3 == 0`，`mvn test` 编译失败 ⇒ 整文件按实测重写。这也是 C3 那个"JDK 9 API 混进 source=8"陷阱的同类现场。
- 我自己写的 6 条断言先后被实测推翻：`getMethods()` 会把继承来的 `Throwable.printStackTrace()` 算成"写方法"；构造器反射顺序是 `[Throwable, String]` 不是声明顺序；`@SPI` 不带 value 时 `getDefaultExtensionName()` 返回 `""` 而不是 null；`AdaptiveExtensionFactory` 连已登记的 `alpha` 都返回 null；`getAddress()` 是 `host + ":" + port` 拼出来的 `"::0"`；JSON 容器往返丢条目。每一条都是改断言、不是改被测代码。

扩展层轮 + 上下文轮 + 跨进程轮留下的五条，第一条正是上一条那个核对步骤的兑现：

- **`uniq -d` 立刻抓到一次跨模块重名**：我给 filter 写的 `bug_traceIdIsPerThreadNotPerCall` 与 async 里已有的 `RpcContextTest.bug_traceIdIsPerThreadNotPerCall` 同名（两个模块各观察了一次"traceId 绑线程"）。计数走的是 `sort -u`，这条会**静默并成一条**，121 会变成 120 而没有任何东西变红。处置是把 filter 那条改名 `bug_traceIdIsStampedOntoEveryCallOfTheThread`，并把"`sort | uniq -d` 为空"当成复算命令的固定第二步。
- **我的修复造成了一次真回归，红的是别人的用例**：`round9b.log` 里 `RegistryDirectoryTest.bug_versionIsDroppedOnTheWayOut` 报 `Service not found`。分诊结论不是"那条用例过时了"，而是**我把兼容路径一起砍了** —— 裸键退回这条路同时承载着"不显式设版本的消费端也能打通"这个契约，而 `RpcRequest.getVersion()` 的缺省值让服务端无法区分"没说要版本"和"要 1.0.0"。收窄后的判据写进 §7 第 25 行，并且**在 remoting 里补了一条正向用例把这个 carve-out 钉住** —— 之前它只作为别的模块用例的副产品存在，所以第一版修复砍掉它时只有 core 喊了一声。
- **`assertNull` 用在了跨进程读回来的字符串上**：子进程把 MDC 里的 Java `null` 打印成文本 `"null"`，父进程拿到的是 4 个字符的字符串而不是 null ⇒ 期望写成 `assertEquals("null", …)`。这类"边界之后形状会变"的断言，必须先确认序列化后的**文本形状**再写下期望（同轮的 `getGroup()` 也犯过一次：期望 `""`、实收 `null`，因为 `Map.getOrDefault` 在"键存在且值为 null"时返回 null）。

### 顺带量到的链路事实：仓里有两套互不兼容的帧格式，而 `z-rpc-serialize` 不在链路上

这不是推测，是 `grep` + 读编码器字节序量出来的：

- **真正跑得通的那套在 `z-rpc-remoting`**：`RpcMessageEncoder` 写 `4 字节魔数 ZRPC + 1 version + 1 msgType + 4 int bodyLen = 10 字节头`，body 用 **Java 原生序列化**（`ObjectOutputStream`）。`RpcClient:53-54` 与 `RpcServer:108-109` 把它接进 pipeline —— C1 修复后跑通的真 socket 往返走的就是这条。
- **另一套 26 字节定长头 + `Serialization` SPI**（就是 H1 修的那个格式）只被 `ZRpcMessageEncoder/Decoder` 使用，而这两个类只被 `ZRpcProtocol` 引用；`ZRpcProtocol`（225 行）**没有 `@SPI`、不在任何 `META-INF/z-rpc/` 元文件里、`src/main` 内零引用**，里面还嵌着 `TestServer`/`TestClient` 两个类 —— 测试脚手架当生产代码提交，且没有 `main`，所以没人能启动它。SPI 登记的名字 `z-rpc` 指向的是 `ZRpcProtocolImpl`。
- **`SerializationFactory` 的生产引用数 = 0**：`grep -rn "SerializationFactory" --include=*.java . | grep -v '/src/test/'` 只命中它自己文件里的 2 行（类声明、logger），**文件外 0 命中**。⇒ **H3 / H4 两条序列化缺陷都落在"离线"模块上**：修它们能让 SPI 层正确，但改不动线上任何一个字节。（H2 同属离线，已在第 18 行修掉；N1 的双份注册表也已在第 19 行合流，但合流只是让两张表一致，**没有**把任何一条链路接到这张表上。）

对优先级的直接影响：想让 `z.rpc.*.serialization=hessian2` 这类配置真正生效，得先把 `ZRpcProtocolImpl` / `RpcClient` / `RpcServer` 接到 26 字节编解码器或 `Serialization` 上去。那是一次**协议统一**决策（要不要废弃 10 字节格式、老客户端怎么办），不是一行修，所以我没动。

### 修一处必须 clean 一次：内联常量的假绿

把 `HEADER_LENGTH` 从 24 改成 26 之后，`z-rpc-protocol` 的用例**照绿**。`javap -c` 给出原因：`static final int` 是编译期常量，会被**逐字节烧进依赖方的字节码**，`ZRpcMessageDecoder` 里仍是 `bipush 24` —— 增量编译看不到 `z-rpc-common` 的改动。所以：

- 判"修好了"必须读字节码，不能只读源码常量：修复轮之后 `javap -c` 里已是 `bipush 26`。
- 复现命令一律带 `clean`；不带 clean 的绿在这一条上不成立。
